# Overview Review

Third pass — conducted against the live text of `documentation/project/overview.md` dated 2026-04-10.

---

## Contradictions

- **Mentor deletion controls vs. Workspace content list (Sections 8.1 and 2.2):** Section 8.1 states the Mentor "cannot be renamed or deleted as a standalone action within the Personas area — these controls are shown as disabled." Section 2.1 states deleting a Workspace "permanently removes all content within it — all Personas, Conversations, Folders, Documents, Mentor history, and Review Agent findings." This is consistent. However, Section 2.2's content areas list only three primary areas: Discussions, Personas, and Documents. The Mentor's sidebar slot (Section 3.1) and its configuration presence in the Personas area (Section 4.1) make it a fourth distinct surface. The document is clear about this in Sections 3.1 and 4.1 but the Section 2.2 summary omits it — a reader relying only on 2.2 would not know the Mentor has a dedicated sidebar zone. This is an omission rather than a strict contradiction, but it could cause requirements to miss the Mentor sidebar slot as a distinct UI requirement.

- **Review Agent access to Conversation history (Sections 7.2 and 7.4):** Section 7.2 states the Review Agent runs analysis on concluded Conversations and evaluates Persona performance against their snapshots. Section 7.4 states the Review Agent does **not** have access to full Conversation histories in interactive consultation mode. These are two distinct modes of the same component and the distinction is called out explicitly, so this is not a true contradiction — but the asymmetry is easy to misread when writing requirements. Worth flagging to ensure requirements specify which context (automated vs. interactive) grants what access.

- **Automatic Summary editability (Section 6.2):** Section 6.2 states "In Version 1, the summary is a fixed system-generated record and cannot be edited or regenerated." Section 6.2 also states "A future version may allow the user to regenerate it with an optional focus prompt." No contradiction, but the word "regenerated" in the future note implicitly confirms regeneration is not available in V1. The requirement to prevent editing and regeneration in V1 needs to be captured explicitly.

## Missing Information

- **Conversation mode change: Round-Robin → 1:1 (Section 5.2 / Mode changes):** The document specifies two mode-change paths: "1:1 → Round-Robin" (triggered by accepting an Orchestrator suggestion) and "Round-Robin → Peer-to-Peer" (triggered by an explicit UI control). It also states that if a Persona is removed and the count drops below the minimum for the current mode, the mode "automatically adjusts — dropping to 1:1." This automatic drop is documented. However, the document does not address whether the user can **manually** switch from Round-Robin to 1:1 (i.e., without removing a Persona to trigger the automatic drop). If no such manual path exists, that is a constraint to be captured in requirements. If one does exist, it needs to be described.

- **Conversation mode change: any mode → Peer-to-Peer (Section 5.2):** Only one mode-change path to Peer-to-Peer is documented: Round-Robin → Peer-to-Peer. It is unclear whether a user can switch directly from 1:1 to Peer-to-Peer (e.g. after adding a second Persona via the Orchestrator, can the user then switch to Peer-to-Peer instead of Round-Robin?). The requirements writer cannot determine the valid state transitions without this.

- **Peer-to-Peer mode — requirements blockage (Section 5.2, Mode 3):** The document explicitly notes Peer-to-Peer "requires further technical research to fully define." This means requirements for that mode cannot be written completely. It should be confirmed whether Peer-to-Peer requirements are in scope for Phase 1 stories, or whether they should be deferred to a later phase pending research outcomes.

- **Test panel — conversation length and persistence (Section 4.5):** The Test panel "maintains a short back-and-forth session." The document does not define what "short" means — is there a message limit? Is the session cleared when the user navigates away from the Persona config page (consistent with the interactive consultation discard behaviour in Section 7.4), or does it persist across navigation? This needs clarification to write a testable requirement.

- **Automatic Conversation naming (Section 3.2):** "If the user has not manually renamed it, the system automatically generates a name on first summarisation of the Conversation." It is not defined what "first summarisation" means in this context — is this the Automatic Summary triggered on ending the Conversation (Section 6.2), or a Targeted Summary (Section 6.3) requested during the Conversation? If it is the Automatic Summary, auto-naming only happens when a Conversation is ended — which may mean that active, long-running Conversations carry "New Conversation [timestamp]" names indefinitely. If it is the Targeted Summary, it happens earlier. This ambiguity will produce conflicting requirements.

- **Report generation timing (Section 6.4):** The overview states the user is "presented with the option to generate a formal Report" upon ending a Conversation (Section 6.1) — but Section 6.4 states a Report can be generated "following a concluded Conversation" and that "multiple Reports can be generated from the same Conversation." It is not clear whether the prompt at end-time is a one-time offer or whether the option to generate additional Reports persists indefinitely from the Conversation view. The Conversation view document links behaviour (Section 6.6) implies the latter, but it is not stated explicitly for the initial end-of-conversation flow.

- **Workspace switching during an active generation (Section 5.5):** The document states an in-progress model response "completes in the background and is waiting when the user returns to that Workspace and reopens the Conversation." It does not state what happens if the user deletes the Workspace before returning, or if the model response fails while running in the background. These edge cases are unaddressed.

- **Mentor — no snapshot but Review Agent applies changes (Section 7.4 / Section 7.2):** Section 7.4 states: "when the user applies a Review Agent finding for the Mentor, the change is applied directly to the Mentor's live System Prompt." Section 7.2 states the Review Agent evaluates each Persona "against the Persona's configuration snapshot from that Conversation." Since the Mentor has no snapshot (its Conversation never ends), it is unclear what configuration baseline the Review Agent uses when evaluating the Mentor's performance. Requirements cannot be written for Mentor review evaluation without this.

- **Memory Inspector — Working Memory (Sections 8.5 and 8.6):** Section 8.5 defines three memory layers: Working Memory, Episodic Memory, and Semantic Memory. Section 8.6 describes the Memory Inspector as showing only two panels: Episodic Memory and Semantic Memory. Working Memory is explicitly absent. If this is intentional (Working Memory is too volatile to inspect usefully), that should be stated. If not intentional, it is a gap. Either way, it needs a clear statement so the requirement for the Memory Inspector panel can be written accurately.

- **Pinned Conversations and Folders (Section 3.1):** The sidebar structure lists Folders at the top, then Pinned Conversations, then Standalone Conversations, then the Mentor slot. It is not stated whether a Conversation inside a Folder can also be pinned — and if so, whether it appears in both the Folder (when expanded) and the Pinned section, or only in the Pinned section. This matters for the sidebar rendering requirement.

- **Review Agent — which Conversations are "new" for the Mentor (Section 7.2):** The document states the Review Agent "analysing the most recent activity since its last review" for the Mentor. It does not define how "last review" is tracked — is it a timestamp recorded per Mentor, or the last nightly run time? If a manual run is triggered between nightly runs, does that reset the Mentor's "since last review" window?

## Undocumented Edge Cases

- **Ending a Conversation mid-cycle in Round-Robin mode:** The document describes the end-of-conversation flow (Section 6.1) but does not address what happens if the user clicks "End Conversation" while a Persona's response is still being generated mid-cycle. Does the in-progress generation complete before the Conversation is ended, or is it aborted? This affects the state of the Automatic Summary.

- **Applying a Review Agent finding while the Persona is active in a Conversation (Section 7.3 / Section 5.6):** A finding can be applied at any time. If the user applies a finding that changes a Persona's System Prompt while that Persona is active in an open Conversation, Section 5.6 states the running Conversation is unaffected (it runs from its snapshot). But the finding application updates the live System Prompt. This interaction is internally consistent but the end state — live prompt updated, running Conversation unaffected — should be explicitly stated in requirements to avoid confusion during implementation.

- **Dismissing a Targeted Summary's Context Panel offer (Section 6.3):** After a targeted summary, "the system may offer a one-click option to add the key points to the Context Panel." The document does not state what happens if the user declines this offer — whether the offer disappears or can be re-invoked. If it can only be accepted once, users may lose the option if they dismiss it accidentally.

- **Report deletion and Conversation view state (Section 6.6):** The document states: "The Conversation view reverts to showing only the 'generate a report' option if all Reports for that Conversation have been deleted." It does not address whether deleted Reports are recoverable or permanently removed. Given a Workspace deletion is permanent and confirmed, Report deletion should be treated the same — but this is not stated.

- **Context Panel at the character limit (Section 5.3):** The document states "If the Context Panel is near its character limit, the system warns the user rather than truncating." It is not clear what happens if the user manually types beyond the limit in the Context Panel editor itself (as opposed to the one-click offer path). Does the editor prevent input beyond the limit? Does it warn and then block, or warn and allow overflow?

- **Workspace with no Conversations when nightly Review Agent runs (Section 7.2):** The Review Agent skips if "no Conversations have concluded since the last run." It is not stated what happens on first run ever — if the system has never run before, is there a concept of "last run time" that defaults to system initialisation, or to some other value?

## Ambiguities

- **"Discussed area" navigation areas vs. four sidebar zones (Section 2.2 vs. Section 3.1):** Section 2.2 names three "primary areas accessible from the main navigation": Discussions, Personas, and Documents. Section 3.1 describes four distinct zones within the Discussions sidebar: Folders, Pinned Conversations, Standalone Conversations, and the Mentor Conversation. The document is clear that the Mentor Conversation lives in the Discussions sidebar — but "main navigation" in Section 2.2 lists only three areas. It is ambiguous whether the Mentor is considered a fourth primary navigation area or a sub-element of Discussions. This affects top-level navigation requirements.

- **"Session" in Mentor context (Sections 8.4 and 8.5):** The document uses "session" to mean a calendar-day-bounded period of Mentor Conversation use (Section 8.4), but does not define whether a "session" ends when the user closes the application, navigates away from the Mentor view, or only at a calendar-day boundary. Working Memory compression is described as triggered by "the end of a session" (Section 8.5) — this trigger is ambiguous if "session" is not precisely defined.

- **Orchestrator suggestion re-suppression (Section 5.4):** "If the user dismisses a suggestion, the Orchestrator will not immediately re-suggest the same Persona." The word "immediately" is undefined — does it mean: not until the topic changes substantially (as stated in the next sentence), or not within the current Conversation, or not within a time window? The next sentence clarifies the re-suggestion condition (substantial topic shift) but the framing "not immediately" creates a gap between "immediately" and "substantial topic shift" that is never resolved.

- **"Ongoing basis" for Mentor Review Agent analysis (Section 7.2):** The Mentor is reviewed "on an ongoing basis — analysing the most recent activity since its last review." This phrasing implies the Mentor is reviewed every nightly run regardless of whether its Conversation has concluded. But the Mentor is also subject to the "no new activity → skipped" rule. The phrase "ongoing basis" is slightly at odds with the nightly batch cadence — a reader could interpret it as continuous or near-real-time review rather than nightly. Requirements should pin this to the nightly schedule to avoid implementation ambiguity.

- **Documents area in Workspace deletion (Section 2.1 vs. Section 6.6):** Section 2.1 states Workspace deletion removes "all Personas, Conversations, Folders, Documents, Mentor history, and Review Agent findings." Section 6.6 states Documents are "Workspace-scoped and subject to the same total isolation rules." This is consistent. However, "Mentor history" in Section 2.1 is not a term defined in the Glossary and does not directly correspond to any named structure (the Mentor's memory layers, its Conversation, its configuration). It is ambiguous what precisely constitutes "Mentor history" for the purposes of a deletion requirement.

- **Context Panel "maximum length" configuration (Section 5.3):** The document states the limit is "a global configuration variable, derived from the deployed model's context window capacity and defined during architecture." It is ambiguous whether this is a single fixed system-wide value or whether it can differ per Workspace (e.g., if different models are configured per Workspace in a future version). In V1, with a single model, this distinction may not matter — but the requirement should specify whether it is system-wide or Workspace-scoped.

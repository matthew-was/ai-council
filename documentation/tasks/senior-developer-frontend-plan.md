## Scope summary

This plan covers the complete React 19 + Vite SPA for AI Council (`apps/frontend/`). It addresses all Phase 1 user stories (US-W1–US-W4, US-P1–US-P5, US-C1–US-C6, US-CP1–US-CP2, US-O1–US-O3, US-L1–US-L3, US-R1–US-R3, US-RA1–US-RA5, US-M1–US-M5, US-MM1–US-MM2, US-AI1). ## Routing Decision

**TanStack Router** is chosen over React Router for the following reasons:

- Type-safe route definitions with full TypeScript inference over path parameters and search parameters — essential for workspace-scoped navigation where `workspaceId`, `conversationId`, `personaId`, and `documentId` must be typed correctly at every call site.
- File-based or code-based route tree with first-class `loader` support: SWR is used for all data fetching, but TanStack Router's `loader` provides the shell for pre-loading critical workspace and conversation data before render, reducing layout-shift.
- Devtools parity with TanStack Query (same ecosystem conventions as SWR-adjacent patterns).
- React Router v7's data-loading API is comparable, but TanStack Router's TypeScript ergonomics are materially stronger, which matters on a codebase that relies on generated `openapi-typescript` types at every layer.

## 2. Routing

All routes are nested under the workspace context. The root layout provides the workspace switcher. The workspace `_layout.tsx` provides the three-area navigation (Discussions, Personas, Documents) and the discussions sidebar.

| Route | Path | Component | Notes |
| --- | --- | --- | --- |
| Root | `/` | `__root.tsx` | Global layout; workspace switcher dropdown |
| Empty / workspace select | `/` (index) | `routes/index.tsx` | Shown when no workspace is active |
| Workspace shell | `/workspaces/$workspaceId` | `_layout.tsx` | Loads workspace detail and persona/conversation/folder lists |
| Discussions empty | `/workspaces/$workspaceId/discussions` | `discussions/index.tsx` | Empty state for discussions area |
| Conversation view | `/workspaces/$workspaceId/discussions/$conversationId` | `discussions/$conversationId/index.tsx` | Conversation thread, context panel, participants |
| Personas list | `/workspaces/$workspaceId/personas` | `personas/index.tsx` | List of all personas; Review Agent run-now button |
| Persona detail | `/workspaces/$workspaceId/personas/$personaId` | `personas/$personaId/index.tsx` | Edit form, test panel, recommendations, memory inspector (if Mentor) |
| Documents list | `/workspaces/$workspaceId/documents` | `documents/index.tsx` | All reports in the workspace |
| Document view | `/workspaces/$workspaceId/documents/$documentId` | `documents/$documentId/index.tsx` | Full report content |

### Route parameters

- `$workspaceId` — UUID v7, required on all workspace-scoped routes.
- `$conversationId` — UUID v7, identifies the conversation. The Mentor Conversation is identified by `is_mentor_conversation: true` in the response; it uses the same route shape.
- `$personaId` — UUID v7.
- `$documentId` — UUID v7.

### Navigation guards

- If no workspaces exist, redirect from `/` to a create-workspace flow.
- If a `$workspaceId` does not resolve (404 from API), redirect to `/` with an error toast.
- If the Mentor slot is clicked and no Mentor Persona exists, navigate to `/workspaces/$workspaceId/personas` with a `?action=create-mentor` search param that triggers the creation prompt.

## 3. Component Architecture

### 3.1 Root Layout (`__root.tsx`)

**Responsibility**: Global shell. Renders the workspace switcher in a top navigation bar. Provides the `<Outlet />` for all nested routes. Fetches the workspace list via `useWorkspaces()`.

**Key state**: Active workspace ID (derived from route `$workspaceId`).

**Props to children**: None — children read workspace ID from route params.

---

### 3.2 Workspace Shell (`_layout.tsx`)

**Responsibility**: Loads the active workspace (including `context_panel_max_chars`), the persona list, the conversation list, and the folder list. Renders the three-area navigation tabs and the `DiscussionsSidebar`. Provides `<Outlet />` for the main area.

**SWR keys fetched here**:
- `GET /workspaces/$workspaceId` → stored in SWR, provides `context_panel_max_chars` to all descendants
- `GET /workspaces/$workspaceId/personas` → persona list for sidebar Persona selector and new-conversation flow
- `GET /workspaces/$workspaceId/conversations` → conversation list for `DiscussionsSidebar`
- `GET /workspaces/$workspaceId/folders` → folder list for sidebar

This layout is the provider boundary for workspace-level data. Child routes do not re-fetch these lists — they read from SWR cache and mutate on change.

---

### 3.3 Discussions Sidebar (`DiscussionsSidebar`)

**Responsibility**: Renders the full sidebar: folders (collapsed by default, expansion inline), pinned conversations, standalone conversations, and the Mentor slot pinned at the bottom.

**Component tree**:

```text
DiscussionsSidebar
├── [Folders section]
│   └── FolderRow (per folder, expandable inline)
│       └── ConversationRow (per conversation in folder)
├── [Pinned section] — only if any pinned standalone conversations exist
│   └── ConversationRow (per pinned standalone)
├── [Standalone section]
│   └── ConversationRow (per unpinned non-folder conversation)
└── MentorSlot (always at bottom, fixed)
```

**Ordering logic (all client-side)**:
- Folders: `created_at` ascending.
- Pinned standalone: `pinned_at` ascending (oldest pin first).
- Standalone: `last_message_at` descending (most recent first). Null `last_message_at` sorts to the bottom.
- Folder conversations: pinned ones first by `pinned_at` ascending, then unpinned by `last_message_at` descending.

**ConversationRow props**: `conversation` object, `isActive` (matched against route), `workspaceId`.

**MentorSlot props**: `mentorConversation` (the Conversation object with `is_mentor_conversation: true`, or null if no Mentor exists), `workspaceId`.

### 3.5 Mentor Conversation View (`MentorConversationView`)

**Responsibility**: Wraps `ConversationView` with Mentor-specific UI. Suppresses participant controls (no add/remove Persona). Shows the manual "Start new chapter" button. Detects `chapter_prompt_required: true` on load and renders `ChapterPromptDialog`.

**PersonaList** (`personas/index.tsx`):
- Renders all personas. Mentor persona is visually distinct (badge or section heading).
- Contains "Run now" button for Review Agent. Disabled when `latest_run.status === 'running'`.
- "New Persona" button. "Create Mentor" button (only shown if no Mentor exists).

**Persona Detail** (`personas/$personaId/index.tsx`):

```text
PersonaDetail
├── PersonaForm
│   ├── Name field (disabled for Mentor with tooltip)
│   ├── Description field
│   ├── System Prompt editor (textarea, multi-line)
│   ├── TemperatureSlider (0.0–2.0; labelled "Precise & Analytical" ↔ "Creative & Exploratory")
```

**TemperatureSlider**: Base UI Slider component, mapped from raw float (0.0–2.0) to display. The slider itself stores and emits the raw float value. Labels are purely visual.

**TestPanel**: Maintains `sessionId` (frontend-generated UUID, generated once on mount, stable for the component lifetime). Has its own local message list (not persisted). Uses `useConversationStream`-equivalent SSE logic via `POST /personas/{persona_id}/test` with SSE response. Disabled state is `isDirty` (PersonaForm has unsaved changes).

### 3.7 Documents Area

**DocumentList** (`documents/index.tsx`): Lists all documents, ordered `created_at` descending. Shows title, status badge (pending/complete/failed), and creation date. Links to Document view for complete documents.

**DocumentView** (`documents/$documentId/index.tsx`): Renders `content_markdown` via `MarkdownRenderer`. Shows a "pending generation" placeholder if `status: pending`. Shows a failure message if `status: failed`. Provides rename, export (triggers browser download via `exportHelpers.ts`), and delete actions.

Documents that are linked from a Conversation view (via `source_conversation_id`) use the same route — the Conversation view renders links as standard TanStack Router `<Link>` elements.

---

### 3.8 Memory Inspector Panel

**Responsibility**: Read-only panel shown on the Mentor's Persona profile page. Two sections: Episodic Memory and Semantic Memory. No edit controls.

**Episodic Memory**: Entries are grouped by `source_type` before rendering. The two groups are displayed under distinct headings:

- **"From Mentor sessions"** — entries with `source_type: 'self'`, ordered by `sequence_number` ascending. These are summaries promoted from the Mentor's own Conversation.
- **"From observed conversations"** — entries with `source_type: 'observed'`, ordered by `sequence_number` ascending. Each card also displays the originating Conversation title or ID from `source_conversation_id` so the user can understand what the Mentor learned and where it came from.

**Semantic Memory**: Each document rendered via `MarkdownRenderer`, ordered by `updated_at` descending. No source grouping — semantic facts are distilled from both source types and presented as a unified long-term view.

**Data**: Fetched via `useEpisodicMemory(workspaceId, personaId)` and `useSemanticMemory(workspaceId, personaId)`. These hooks only make valid requests when the persona has `is_mentor: true` — the backend enforces this with a 403, but the frontend guards the request.

### 3.9 Shared Components

- **ConfirmDialog**: Reusable destructive-action dialog. Props: `title`, `description`, `confirmLabel`, `onConfirm`, `onCancel`.
- **InlineEditable**: Renders as text when idle, switches to an input on click. Calls `onSave(newValue)`. Used for conversation title, workspace name, document title, folder name rename flows.
- **MarkdownRenderer**: Wraps a Markdown-to-HTML renderer (e.g. `react-markdown` with sanitisation). Used for report content, semantic memory documents, auto-summary copy, targeted summary display.
- **EmptyState**: Displays an icon, heading, description, and optional CTA button. Used across all empty list states.
- **ErrorBanner**: Inline error display. Accepts a normalised `ApiError` object from `lib/apiError.ts`.
- **LoadingSpinner**: Simple spinner used for loading states across the application.

## 4. State Management

Per ADR-013: no global state management library. State is managed at two levels:

### 4.1 Server state (SWR)

All data that originates from the backend is managed by SWR. Cache keys are strings following the API path pattern. Mutations use `mutate()` to update the cache optimistically or after a confirmed server response.

Key SWR cache keys:

| Hook | SWR key | Endpoint |
| --- | --- | --- |
| `useWorkspaces` | `'/workspaces'` | `GET /workspaces` |
| `useWorkspace(id)` | `'/workspaces/${id}'` | `GET /workspaces/${id}` |
| `usePersonas(wsId)` | `'/workspaces/${wsId}/personas'` | `GET /workspaces/${wsId}/personas` |
| `usePersona(wsId, pid)` | `'/workspaces/${wsId}/personas/${pid}'` | `GET /workspaces/${wsId}/personas/${pid}` |

### 4.2 Client-side state (React state / refs)

Local state is co-located with the component that owns it:

- **PersonaForm**: `isDirty` (boolean), controlled field values. `isDirty` is shared upward to `TestPanel` via a prop or context to disable it.
- **MessageList**: Cursor for pagination (`oldestLoadedMessageId`), `hasMore` flag, `isLoadingMore` flag — managed in a `useReducer` inside `useMessages`.
- **FolderRow**: `isExpanded` boolean.
- **InlineEditable**: `isEditing`, `draftValue`.
- **ContextPanel**: `draftContent`, `characterCount`, `isOverLimit`, `isDirty`.
- **ConsultationPanel**: `sessionId` (stable UUID generated on mount), local message list, streaming buffer.
- **TestPanel**: `sessionId`, local message list, streaming buffer.

### 4.3 Conversation state machine

See Section 8 for the full state machine. The state object lives in a `useRef`-backed store local to `ConversationView`/`MentorConversationView`. It is not lifted to a React context because only one Conversation view is open at a time per browser tab.

## 5. Data Fetching

### 5.1 `apiClient` and workspace context header

`src/api/client.ts` is the central fetch wrapper for all HTTP requests. It:
- Prefixes all URLs with `config.api_base_url`.
- Sets `Content-Type: application/json` on POST/PATCH.
- On non-OK responses, calls `normaliseApiError(response)` before throwing.

**`X-Workspace-ID` header for non-workspace-scoped endpoints**: Several API endpoints are not nested under `/workspaces/{workspace_id}/` but still require workspace context to be communicated to the backend. These are:

- `POST /personas/{id}/test`
- `POST /personas/{id}/consultation`
- `GET /conversations/{id}/stream`
- `POST /conversations/{id}/pause`
- `POST /conversations/{id}/resume`
- `POST /conversations/{id}/cancel`
- `POST /conversations/{id}/suggestions/{sid}/accept`
- `POST /conversations/{id}/suggestions/{sid}/dismiss`

For all requests to these endpoints, `apiClient` reads the active `workspaceId` from the current TanStack Router route context (the `$workspaceId` path parameter, available at every route within the workspace shell) and includes it as an `X-Workspace-ID` request header. The header injection is applied in `client.ts` based on a URL-pattern check against the list of non-workspace-scoped endpoint prefixes above. All other requests (workspace-scoped endpoints under `/workspaces/{workspace_id}/`) do not require this header — workspace context is established by the URL path on those endpoints.

### 5.2 SWR configuration

A global SWR config provider is set at the root of the application:

```ts
// In main.tsx or a dedicated SWRProvider component
<SWRConfig value={{
  fetcher: (url: string) => apiClient.get(url),
  revalidateOnFocus: false,       // AI Council is a single-tab local tool
  dedupingInterval: 2000,
  shouldRetryOnError: false,      // API errors are shown to the user, not silently retried
}}>
```

`revalidateOnFocus: false` is set because the application is expected to be used in a single tab on a local machine; background revalidation on tab focus adds noise without benefit.

### 5.3 Loading states

Every SWR hook returns `{ data, error, isLoading }`. Components follow this pattern:

- `isLoading && !data` → render `<LoadingSpinner />` or skeleton
- `error` → render `<ErrorBanner error={normaliseApiError(error)} />`
- `data` → render content

### 5.4 Mutations and cache invalidation

All mutations use `apiClient` directly (not SWR's `mutate` directly), then call `mutate(key)` to revalidate:

- **Optimistic updates** are used for: renaming a conversation, updating `pinned_at`, renaming a folder, renaming a document, renaming a workspace. These are low-risk mutations where the API almost never rejects a valid value.
- **Non-optimistic** (wait for server confirmation): creating/deleting workspaces, personas, conversations, folders; applying/dismissing findings; accepting/dismissing Orchestrator suggestions; adding/removing participants. These either have meaningful error states (409 conflicts) or produce server-generated data (IDs, timestamps) that the client cannot predict.

### 5.5 Conversation message pagination

`useMessages` implements cursor-based infinite scroll. The hook manages a local array of pages. The first call fetches the most recent page (no `before` cursor). As the user scrolls to the top of `MessageList`, the hook fetches the next page using the oldest loaded message ID as the `before` cursor. Pages are prepended to the array (messages render top-to-bottom, oldest first). `has_more` controls whether the scroll trigger continues to fire.

### 5.6 Polling for async operations

Two backend operations are async and require the frontend to poll for completion:

**Auto-summary** (after `POST /end`): When the Conversation is ended and the response has `auto_summary: null`, `useConversation` is configured with a `refreshInterval` of 3000ms. The interval is active only when `data.status === 'ended' && data.auto_summary === null`. It stops automatically once `auto_summary` is populated.

**Report generation** (after `POST /documents/generate`): `useDocument(wsId, did)` is configured with a `refreshInterval` of 3000ms, active only when `data.status === 'pending'`. Stops when `status` transitions to `complete` or `failed`.

These are the only two places in the application where SWR `refreshInterval` is used.

## 6. SSE Client

### 6.1 Architecture

`src/api/sse.ts` exports a `ConversationStream` class that wraps `@microsoft/fetch-event-source`. One instance exists per open Conversation view and is created/destroyed by `useConversationStream`.

```ts
class ConversationStream {
  open(conversationId: string, workspaceId: string, handlers: SSEHandlers): void
  close(): void
}

type SSEHandlers = {
  onToken: (payload: TokenEvent) => void
  onResponseComplete: (payload: ResponseCompleteEvent) => void
  onOrchestratorSuggestion: (payload: OrchestratorSuggestionEvent) => void
  onBusy: () => void
  onIdle: () => void
  onPaused: () => void
  onExchangePaused: (payload: ExchangePausedEvent) => void
  onError: (error: Error) => void
}
```

The SSE URL is `GET /conversations/{conversationId}/stream` relative to `config.api_base_url`. Because this endpoint is not under `/workspaces/{workspace_id}/`, the SSE client includes an `X-Workspace-ID` header in the `fetch-event-source` request options when opening the stream. The `workspaceId` is passed into `ConversationStream.open()` and set as `headers: { 'X-Workspace-ID': workspaceId }` in the `EventSourceInit` options object passed to `@microsoft/fetch-event-source`.

### 6.2 `useConversationStream` hook

```ts
function useConversationStream(
  conversationId: string | null,
  workspaceId: string,
  handlers: SSEHandlers
): { isConnected: boolean }
```

- Opens the stream on mount (or when `conversationId` changes from null to a value).
- Closes the stream on unmount or when `conversationId` becomes null.
- `@microsoft/fetch-event-source` handles reconnection automatically via `Last-Event-ID`.
- The hook passes a stable `handlers` ref to avoid re-opening the stream on handler identity change.

### 6.3 Stream lifecycle

The stream is opened when `ConversationView` (or `MentorConversationView`) mounts with a `conversationId`. It is closed when the component unmounts (navigation away). For the Mentor Conversation, stream close on navigation is the signal that the user has left the session — the backend handles the rest (Working→Episodic compression runs on the scheduled APScheduler job, not on stream close, per FC-5 resolution).

### 6.4 Token accumulation

When a `token` event arrives, the token's `content` is appended to a mutable ref (`streamingBufferRef`) keyed by `conversation_persona_id`. The buffer keys are plain strings and may be either a standard UUID (for regular Persona turns) or the prefixed format `"mentor:{uuid}"` (for Mentor turns) — the `streamingBufferRef` uses the raw `conversation_persona_id` string as the key in both cases without any special-casing. The accumulated buffer is displayed in `StreamingBubble` via a React state update triggered by a `flushSync`-free batched update on a `requestAnimationFrame` cadence to avoid excessive renders. When `response_complete` arrives, the buffer for that `conversation_persona_id` key is cleared, and the canonical `content` from the event replaces the streaming text.

`StreamingBubble` is a single component rendered below the `MessageList`. It shows the currently streaming Persona's name (looked up from the SWR personas cache by resolving the `conversation_persona_id` — see Section 6.5) and the accumulated buffer. It is removed from the DOM on `idle`.

### 6.5 Mentor stream `conversation_persona_id`

The backend defines the Mentor Conversation's `conversation_persona_id` in SSE `token` and `response_complete` events as a synthetic string with the format:

```text
"mentor:{persona_id}"
```

Where `{persona_id}` is the Mentor Persona's UUID. For example, if the Mentor Persona has ID `018e1234-0000-7000-8000-000000000001`, the value is `"mentor:018e1234-0000-7000-8000-000000000001"`.

The frontend identifies Mentor token events by checking whether the `conversation_persona_id` value starts with the prefix `"mentor:"`. When this prefix is detected:

1. The UUID suffix is extracted by stripping the `"mentor:"` prefix: `const personaId = conversationPersonaId.slice('mentor:'.length)`.
2. The Mentor Persona's display name is looked up by `personaId` from the SWR personas cache (`usePersonas` result for the current workspace). Since the Mentor Conversation has no `conversation_personas` rows, the display name is always resolved from the personas cache in this way.

The `streamingBufferRef` stores the token content under the full `"mentor:{uuid}"` key without modification — no special-casing is needed at the buffer level. The display name resolution only happens in `StreamingBubble` when rendering the speaker label.

This logic is documented in `useConversationStream` and `StreamingBubble` at the point of use.

### 6.6 Test panel and consultation panel SSE

Both `TestPanel` and `ConsultationPanel` use the same SSE client path via `ConversationStream` (or a lightweight equivalent — they use `POST` endpoints that return SSE streams). A helper `openEphemeralStream(url, body, handlers, workspaceId)` function in `sse.ts` handles one-shot SSE for these cases. The `sessionId` in the request body is the only session management required. The `workspaceId` is included as an `X-Workspace-ID` header in the request, because `POST /personas/{id}/test` and `POST /personas/{id}/consultation` are non-workspace-scoped endpoints (see Section 5.1).

## 8. Conversation State Machine

### 8.1 States

The frontend tracks the following conversation states:

| State | Meaning | Available controls |
| --- | --- | --- |
| `idle` | No AI processing in progress | Send message, Add/Remove Persona, Mode switch, Export, End, Pause (disabled), Resume (hidden) |
| `busy` | AI is generating a response | No send, no Add/Remove, no Mode switch, no Export. Cancel button shown in P2P. End Conversation allowed (backend handles gracefully). |
| `paused` | Conversation paused (Workspace-switch interrupt or user-initiated pause in non-P2P) | Resume button shown. No send. |
| `exchange_paused_user` | P2P exchange paused by user | Resume button shown. No send (except via Resume). |
| `exchange_paused_turn_cap` | P2P exchange hit turn cap | Message input shown with prompt to continue. No Resume button. |
| `exchange_paused_repetition` | P2P exchange detected repetition | Message input shown with steering prompt. No Resume button. |
| `ended` | Conversation ended | Read-only. No controls except Export and Report generation. |

### 8.2 State transitions

State is driven by SSE events and local actions:

```text
SSE `busy`          → state = 'busy'
SSE `idle`          → state = 'idle'
SSE `paused`        → state = 'paused'
SSE `exchange_paused` (pause_reason: 'user_pause')          → state = 'exchange_paused_user'
SSE `exchange_paused` (pause_reason: 'turn_cap')            → state = 'exchange_paused_turn_cap'
SSE `exchange_paused` (pause_reason: 'repetition_detected') → state = 'exchange_paused_repetition'

User sends message in turn_cap or repetition state          → state = 'busy' (optimistically, confirmed by next `busy` SSE)
User clicks Resume in paused or exchange_paused_user state  → POST /resume → state stays 'paused' until SSE `busy` received
POST /end response received                                 → state = 'ended'
POST /end response received with deleted: true              → navigate away (conversation deleted)
```

### 8.3 Initial state on stream open

When `ConversationView` mounts for an `active` conversation, the SSE stream is opened immediately. The initial local state is set to `idle`. If the conversation was paused due to a workspace-switch interrupt, the backend will emit a `paused` event as the first event on stream re-open, which transitions the state machine to `paused` and shows the Resume button. The existing `SSE 'paused' → state = 'paused'` transition in the state machine handles this — no additional logic is required. The frontend does NOT call `GET /conversations/{id}` before opening the stream to detect paused state independently.

For an `ended` conversation, no stream is opened and the state is immediately `ended`.

### 8.4 Implementation

The state machine is a `useReducer` hook in `ConversationView`. The reducer takes `SSEEvent | UserAction` as input and produces the next `ConversationUIState`. The `useConversationStream` hook dispatches SSE-derived actions to this reducer. User actions (click send, click pause, click end) also dispatch actions through the reducer.

```ts
type ConversationUIState = {
  status: ConversationStatus  // the enum above
  pendingSuggestion: OrchestratorSuggestionEvent | null
  streamingPersonaId: string | null
}
```

## 9. Mentor-Specific Handling

### 9.1 Identifying the Mentor Conversation

In the Conversation list, the Mentor Conversation has `is_mentor_conversation: true`. `DiscussionsSidebar` identifies it and renders it in `MentorSlot` at the bottom of the sidebar. The Mentor Conversation uses the same `$conversationId` route but `ConversationView` checks `is_mentor_conversation` and renders `MentorConversationView` instead.

### 9.2 Chapter detection on load

When `useConversation` resolves for the Mentor Conversation:
- If `chapter_prompt_required: true` → `ChapterPromptDialog` is shown immediately.
- The user may choose "Continue" (dialog dismissed, no API call) or "Start fresh chapter" (calls `POST /workspaces/$wsId/conversations/$cid/chapter`, which inserts a `chapter_boundary` system message and returns it for insertion into the message list).
- If the user begins typing before choosing, the dialog is dismissed (continuation assumed).

### 9.3 Chapter marker rendering

Messages with `message_subtype: 'chapter_boundary'` are rendered by `ChapterBoundaryMarker` instead of `SystemMessageMarker`. The visual treatment is a full-width horizontal rule with a "New Chapter" label — visually distinct from join/leave events.

### 9.4 Memory Inspector

`MemoryInspectorPanel` is rendered on the Mentor's Persona detail page (checked via `persona.is_mentor === true`). It is a collapsible panel below the `RecommendationsSection`. It fetches episodic and semantic memory only when expanded, to avoid unnecessary API calls on every Persona page load.

Episodic entries from `useEpisodicMemory` are split into two arrays by `source_type` before rendering: `selfEntries` (`source_type === 'self'`) and `observedEntries` (`source_type === 'observed'`). Each group renders under its own labelled heading. `observedEntries` cards include a secondary line showing `source_conversation_id` (or a resolved Conversation title if available from the SWR cache) so the user can identify the origin of each observation.

### 9.5 Mentor Conversation constraints

`MentorConversationView` enforces these constraints at the component level:
- No participant panel controls (no add/remove Persona).
- No mode selector.
- No End Conversation button (the Mentor Conversation is never ended).
- Manual "New Chapter" button is rendered in the conversation header.

## 10. Review Agent UI

### 10.1 Findings list

`RecommendationsSection` renders two logical groups from the findings array:

**Active findings** (`status: 'active'`): Each `FindingCard` shows `evidence_text` (verbatim quote), `suggestion_text` (proposed System Prompt change), and two action buttons: **Apply** and **Dismiss**.

- Apply: `POST /workspaces/$wsId/personas/$pid/findings/$fid/apply`. On success, the response includes the updated Persona with the new `system_prompt`. The frontend removes the card from the list, updates `usePersona` SWR cache with the new `system_prompt`.
- Dismiss: `POST /workspaces/$wsId/personas/$pid/findings/$fid/dismiss`. On success, the card is removed from the list.
- Both buttons show an in-progress spinner while the request is in flight. The card is removed optimistically on success (the SWR `useFindings` cache is mutated).

**Stale findings** (`status: 'stale'`): Each `FindingCard` is rendered with a visual distinction (e.g. reduced opacity, amber border, "outdated" badge). No Apply or Dismiss buttons. An inline message reads: "This suggestion is outdated — run the Review Agent to update it." The existing "Run now" button in the Personas area provides the action.

### 10.2 Review Agent run status

`useReviewAgentStatus` fetches on Persona area mount. The "Run now" button is disabled when `latest_run?.status === 'running'`. After triggering a run (`POST /review-agent/run`), the button is immediately disabled. There is no background polling — the user refreshes the Personas area or navigates away and back to check completion.

### 10.3 Consultation panel (`ConsultationPanel`)

`ConsultationPanel` is an expandable right-hand panel in the Persona detail page.

- Expanding it generates a new `sessionId` (UUID v7, crypto-random) if one does not yet exist for this mount.
- Each message send: `POST /personas/$pid/consultation` with `{ message, session_id }` and `X-Workspace-ID` header set to the active workspace ID (see Section 5.1 — this endpoint is non-workspace-scoped). The response is an SSE stream of `token` and `response_complete` events delivered via `openEphemeralStream` from `sse.ts`, which includes the `X-Workspace-ID` header in the request.
- The panel maintains its own local message history for the current session. Messages are not persisted.
- On unmount (navigation away from the Persona page), the session is discarded. No explicit session-close call is made to the backend (the backend handles inactivity timeout).

## 11. Orchestrator Suggestion Handling

### 11.1 Receiving a suggestion

When the SSE stream emits `orchestrator_suggestion`, the payload is stored in `conversationState.pendingSuggestion`. `OrchestratorSuggestionBanner` renders when `pendingSuggestion` is non-null.

The banner is non-intrusive: it appears as a fixed notification bar at the top of the message thread (not a modal), showing `suggested_persona_name` and `reason`. Two buttons: **Add [name]** and **Dismiss**.

Only one suggestion is displayed at a time. If a new `orchestrator_suggestion` event arrives while one is already pending, it replaces the previous one.

### 11.2 Accepting a suggestion

`POST /conversations/$cid/suggestions/$sid/accept` (where `$sid = pendingSuggestion.suggestion_id`).

On success:
- `conversation_persona` from the response is added to the participant list (SWR `useConversation` cache mutated).
- `system_message` from the response is appended to the message list.
- `updated_mode` in the response updates the displayed mode (the mode may have switched from `one_to_one` to `round_robin`).
- `pendingSuggestion` is cleared.

### 11.3 Dismissing a suggestion

`POST /conversations/$cid/suggestions/$sid/dismiss`.

On success: `pendingSuggestion` is cleared. The banner disappears.

### 11.4 Suggestion availability

The Add button in `OrchestratorSuggestionBanner` is disabled while the conversation is not idle (state is `busy`). A tooltip explains: "Cannot add a Persona while a response is in progress." The dismiss button is always available.

## 12. Error Handling

### 12.1 `apiClient` and `normaliseApiError`

`src/api/client.ts` is the single entry point for all HTTP requests. See Section 5.1 for full `apiClient` behaviour including the `X-Workspace-ID` header injection for non-workspace-scoped endpoints.

`src/lib/apiError.ts`:

```ts
type ApiError = {
  status: number
  message: string
  code?: string
  // For 409 Persona deletion conflicts:
  blocking_conversations?: Array<{ id: string; title: string }>
  // For 422 validation errors:
  validationErrors?: Array<{ field: string; msg: string }>
}

function normaliseApiError(response: Response): Promise<ApiError>
```

The function reads the response body, attempts JSON parse, and falls back to a generic message if the body is not JSON (handles gateway 502 HTML pages gracefully).

### 12.2 User-facing error display

- **Form validation (422)**: field-level error messages shown below the relevant input.
- **Conflict errors (409)**:
  - Persona delete blocked: `ConfirmDialog`-style overlay listing the blocking conversations by title.
  - Mentor delete blocked: tooltip-only on the disabled delete button.
  - Conversation busy: toast notification ("Cannot modify participants while a response is in progress").
  - Review Agent already running: inline message in the Personas area.
  - Report generation in progress: the Generate Report button is replaced with "Generation in progress."
- **Not found (404)**: navigates to the parent route and shows an `ErrorBanner`.
- **Server errors (5xx)**: `ErrorBanner` with a generic message. No retry logic (per global SWR config `shouldRetryOnError: false`).
- **Non-JSON gateway errors**: handled in `normaliseApiError`; shown as a generic 5xx error.

### 12.3 SSE reconnection failure

`@microsoft/fetch-event-source` retries automatically with exponential backoff. If reconnection fails after the configured number of retries, `onError` is called. `ConversationView` shows a persistent `ErrorBanner` with a "Reconnect" button that calls `stream.close()` then `stream.open()`. The conversation state is not reset — the state machine remains in whatever state it was in before disconnection.

### 12.4 Context Panel over-limit

The frontend computes `characterCount = draftContent.length` and compares against `workspace.context_panel_max_chars`. If over-limit: the character counter turns red, a warning message appears, and the Save button is disabled. The input continues to accept text (per the product spec). If the user somehow bypasses the client-side guard and the backend returns a 422 `CONTEXT_PANEL_TOO_LONG` error, the error is displayed inline below the Context Panel.

## 14. Testing Strategy

### 14.1 Unit tests (Vitest)

Unit tests cover logic that is complex, branching, or easy to get wrong:

- `lib/apiError.ts` — normalisation of all error shapes including non-JSON responses.
- `lib/sseEvents.ts` — type guards for each SSE event type.
- `stores/conversationState.ts` — the state machine reducer: all valid and invalid transitions.
- `hooks/useMessages.ts` — pagination logic: page prepending, cursor management, `has_more` handling.
- `DiscussionsSidebar` ordering logic — given a mix of pinned, standalone, and folder-assigned conversations with various timestamps, assert correct sort order.
- Config loading (`config/index.ts`) — valid and invalid config shapes against the Zod schema.

### 14.2 Hook tests (Vitest + MSW)

Every SWR data-fetching hook has a dedicated test file covering the happy path and all documented error responses. MSW intercepts `fetch` at the network boundary; test fixtures return the contract-defined response shapes typed against `src/api/schema.ts`.

**Standard test structure per hook:**

- **Happy path**: MSW handler returns the contract `200` response; assert the hook's returned data matches the fixture.
- **404 Not Found**: MSW handler returns `{ message: "...", code: "..." }` with status 404; assert the hook surfaces the normalised `ApiError` with the correct `code`.
- **403 Forbidden**: where applicable (e.g. Memory Inspector hooks called against a non-Mentor Persona); assert the `ApiError` is surfaced correctly.
- **Network error**: MSW handler throws a network failure; assert the hook surfaces an `ApiError` with `code: 'network_error'`.
- **Loading state**: assert `isLoading` is `true` before the MSW response resolves.

**Hooks to cover** (one test file each):

| Hook | Expected error codes to test |

| `useWorkspaces` | network error |
| `useWorkspace` | 404, network error |
| `usePersonas` | 404 (workspace), network error |

| `useConversations` | 404 (workspace), network error |

### 14.3 Component tests (Vitest + Testing Library)

Component tests cover rendered behaviour:

- `TemperatureSlider` — slider renders with correct labels; emits correct float value on change.
- `ContextPanel` — character count updates correctly; over-limit state shows warning and disables Save; under-limit enables Save.
- `ExchangePausedBanner` — renders correct message and recovery path for each `pause_reason`.
- `OrchestratorSuggestionBanner` — renders suggestion text; accept and dismiss calls are made with correct `suggestion_id`.

### 14.4 Accessibility tests (Vitest + vitest-axe)

Every component that has a component test (Section 14.3) also has a co-located accessibility assertion using `vitest-axe`. The assertion runs `axe` against the rendered component and expects no violations:

```ts
import { axe } from 'vitest-axe'
import 'vitest-axe/extend-expect'

it('has no accessibility violations', async () => {
  const { container } = render(<FindingCard finding={activeFinding} />)
```

`vitest-axe` is added to `devDependencies`. The `axe` check runs as part of the standard `vitest` test run — no separate test command is required.

### 14.5 SWR and SSE mocking patterns

**SWR mocking**: MSW (Mock Service Worker) intercepts `fetch` at the network boundary. Test fixtures return the contract-defined response shapes typed against `src/api/schema.ts`. MSW handlers are defined in `src/tests/handlers/` and composed per test file.

**SSE mocking**: `@microsoft/fetch-event-source` uses `fetch` under the hood. Tests that exercise SSE behaviour use a mock `fetch` that returns a `ReadableStream` emitting a pre-defined sequence of SSE-framed events. The `useConversationStream` hook is tested by asserting that the correct `handlers` callbacks are called with the correct payloads when the mock stream emits each event type.

**No e2e tests in V1**: Integration against a real backend is deferred. All tests run against the MSW mock layer.

### 14.6 Testing approach for state machine

The `conversationState` reducer is a pure function: given a current state and an action, it returns the next state. This is tested exhaustively with unit tests covering all state × action combinations, including invalid combinations (e.g. `busy` event while already `busy`, `resume` when not paused).

```ts
import { z } from 'zod'

export const FrontendConfigSchema = z.object({
  api_base_url: z.string().url(),
})

export type FrontendConfig = z.infer<typeof FrontendConfigSchema>
```

The nconf loader reads and merges the two JSON files, passes the result through `FrontendConfigSchema.parse()`, and throws on failure. The validated config object is exported as `config` and used throughout the application.

### 15.4 `CONTEXT_PANEL_MAX_CHARS`

This value is **not** in `frontend/config.json`. It is embedded in the Workspace API response (`context_panel_max_chars` field on every Workspace object, per the API contract). The workspace shell layout reads it via `useWorkspace(workspaceId)` and passes it to `ContextPanel` as a prop. It is never cached in component state independently — it is always read fresh from the SWR-cached Workspace object.

## Cross-cutting Concerns

### Conversation Export (US-R3)

`GET /workspaces/$wsId/conversations/$cid/export` returns a `text/markdown` response with `Content-Disposition: attachment` header. `exportHelpers.ts` handles this by:

1. Making a raw `fetch` call (not through the SWR layer).
2. Receiving the response as a `Blob`.
3. Creating a temporary `<a>` element, setting `href` to a blob URL and `download` to the filename from the `Content-Disposition` header, then clicking it programmatically.
4. Revoking the blob URL after the click.

This pattern is used for both Conversation export and Report export (the Report export sends the user to `DocumentView` which downloads `content_markdown` as a file via the same helper).

### Persona snapshot staleness check (US-C5)

`ConversationView` computes staleness for each active participant:

```ts
const isStale = participant.persona_id != null &&
  personaMap[participant.persona_id]?.updated_at > participant.joined_at
```

Where `personaMap` is derived from the `usePersonas` SWR cache. If `persona_id` is null (Persona deleted), the refresh control is suppressed. The `SnapshotRefreshControl` is rendered only when `isStale && conversationState.status === 'idle'`.

### Workspace switch interrupt handling (US-W4)

When the user navigates to a different workspace (changes `$workspaceId` in the route), `ConversationView` unmounts, which triggers stream close in `useConversationStream`. On return to the original workspace and conversation, the stream is opened immediately — no prior state check via `GET /conversations/{id}` is performed. If the conversation was paused due to the workspace-switch interrupt, the backend emits `paused` as the first event on stream re-open. The existing state machine transition (`SSE 'paused' → state = 'paused'`) handles this and shows the Resume button. No special workspace-switch code path is needed in the frontend.
